# 開発者向け警告マニュアル (Developer's Warning Manual)

## ⚠ はじめに
本ドキュメントは、HOROSからJavaへの移植において、**「仕様書通りに実装しても動作しない」**または**「致命的なバグを誘発する」**ことが判明している実装上の罠（Pitfalls）をまとめたものである。実装者は、コードを書き始める前に必ず本マニュアルを熟読すること。

---

## 1. UI/インタラクションの罠

### 1.1 `isKeyView` の不透明な状態遷移
- **現象**: ツールを切り替えた際に、マウスイベントが期待通りに動作しなかったり、フォーカスが外れたりする。
- **罠**: `isKeyView` は単純なBooleanフラグではない。`mouseMoved` $ → $ `computeMagnifyLens` $ → $ `makeFirstResponder` という一連の連鎖により、OSレベルの「第一応答者」が切り替わることで間接的に制御されている。
- **対策**: Java Swingでは `FocusTraversalPolicy` や `KeyboardFocusManager` を適切に制御し、マウスカーソルがビューア領域に入った瞬間にフォーカスを強制的に奪うロジックを実装すること。

### 1.2 ビューア同期の無限ループ (Recursive Sync)
- **現象**: 2つ以上のビューアを同期させた際、`StackOverflowError` が発生してアプリケーションがクラッシュする。
- **罠**: ビューアAの更新 $ → $ 同期イベント発行 $ → $ ビューアBが受信し更新 $ → $ ビューアBが同期イベント発行 $ → $ ビューアAが受信... という無限ループが発生する。
- **対策**: `avoidRecursiveSync` というガードフラグを導入し、同期イベントの処理中は、そのイベント起因の更なる通知を無視する再帰防止ガードを必ず実装すること。

## 2. DICOM / ネットワークの罠

### 2.1 dcm4che Association のリソースリーク
- **現象**: PACSサーバーとの通信を繰り返すと、次第にメモリ使用量が増大し、最終的にサーバー側から接続を拒否される。
- **罠**: `org.dcm4che3.net.Association` クラスは `AutoCloseable` を実装していない。`try-with-resources` では閉じられない。
- **対策**: 必ず `finally` ブロックで以下の手順を完遂すること。
  ```java
  try {
      // 通信処理
  } finally {
      if (assoc != null) {
          assoc.release();
          assoc.waitForSocketClose();
      }
  }
  ```

### 2.2 Pixel Spacing の無視による「拡大・縮小問題」
- **現象**: CT画像は正常だが、CR画像やUS画像を表示すると、極端に拡大されていたり、端が切れたりする。
- **罠**: ピクセル数（Width/Height）をそのまま画面座標にマッピングしているため。DICOMの `Pixel Spacing (0028,0030)` はモダリティによって大きく異なる。
- **対策**: 描画および計測のすべての計算において、`S_x = pixelSpacingX * pWidth` のように物理的なピクセル間隔を乗算した「実世界座標」を基準に計算すること。

## 3. メモリとパフォーマンスの罠

### 3.1 巨大配列によるGC停止 (Stop-the-World)
- **現象**: 大量のスライスを持つボリュームデータを読み込んだ際、UIが数秒間完全にフリーズする。
- **罠**: `float[]` や `ArrayList<Float>` で数千万個のピクセル値を保持すると、GC（ガベージコレクション）のマーク＆スイープに膨大な時間がかかる。
- **対策**: ボリュームデータは `java.nio.ByteBuffer.allocateDirect()` を使用した**オフヒープメモリ**に保持し、`FloatBuffer` 経由でアクセスすること。これによりGCの管理対象から外れ、フリーズを回避できる。

### 3.2 3D再サンプリングの計算コスト
- **現象**: CPR（曲面再構成）のパスを変更した際、表示の更新に時間がかかり、操作感が著しく低下する。
- **罠**: 三線形補間（Trilinear Interpolation）は1ピクセルあたり8回のメモリ参照を行うため、非常に重い。
- **対策**: 
  1. **LOD (Level of Detail)**: パス編集中はサンプリング間隔を 2倍・4倍と粗くし、確定後に高精細に再計算する。
  2. **並列処理**: `Parallel Stream` を用い、CPUの全コアを利用して断面の各列を独立して計算すること。
